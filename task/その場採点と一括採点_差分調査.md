# その場採点と一括採点 — 差分調査メモ

調査日: 2026-04-08（会話ベース）  
対象: Word / Excel / PowerPoint

## 結論（優先度）

| アプリ | その場〇／一括×の起きやすさ | いまの判断 |
|--------|------------------------------|------------|
| **Word** | ほぼ起きにくい | 追加対応は急がない |
| **PowerPoint** | 中間（Word 寄りだが未達） | 経路共通より **証跡確定・reopen 差分** |
| **Excel** | 相対的に起きやすい | **採点経路の共通化** ＋ 証跡確定。実装はアプリで〇✖確認できるタイミングで |

アプリが開けず差分確認できないうちは、**実装より本メモの方針確認を優先**する。

---

## 共通の整理

両方とも「同じチェッカー DLL を呼ぶ」ことが多く、差の本質は次のいずれか。

1. **文書ライフサイクル** … 開いたまま採点 vs 保存→閉じて再オープン  
2. **ログの役割** … 正答証跡（Executed 等）と破壊検知（`[Op]` / snapshot）の混在  
3. **採点経路の二重実装** … 呼び出し方・ゲート適用タイミングの差  
4. **採点後〜一括前の追加操作** … その場で〇を見たあと破壊的操作をすると一括だけ ×（3アプリ共通）

「ログに正答条件以外も入っている」＝ `%TEMP%` の操作ログに **正答用 Executed と破壊検知用 `[Op]` 等が同居**している、という意味（特に Word で明示コメントあり）。

## Word

### アーキテクチャ

| | その場 | 一括 |
|--|--------|------|
| 入口 | `UiTestAppBarWindow` 採点ボタン | レビュー経由 `WordBatchScoring.ScoreAllProjects` |
| 文書 | 開いたまま | 保存→閉じて再オープン |
| 本体 | 同一 Checker DLL + `WordGradingGate` | 同左（`WordBatchScoring`） |
| 証跡 flush | 採点開始時に必ず | レビュー前（最終タスク）＋条件付きフォールバック |

主要ファイル:

- `MOSapp/MOS Word app/Libraries/WordBatchScoring.cs`（ゲート順・記録種類のコメント）
- `MOSapp/MOS Word app/Libraries/LogReader.cs`
- `MOSapp/MOS Word app/Views/UiTestAppBarWindow.xaml.cs`
- VSTO: `New_MOSWordVSTOAddIn`（離脱時・採点直前の証跡補記）

### ログの種類（同一 `mos_word_log.txt` 等）

- **Executed** … 正解証跡（チェッカーの ○ 判定）
- **`[Op]`** … 破壊検知用（許可外ならゲートで ✖）
- **TaskStart** … Op 区間境界
- **snapshot / destructive_errors** … リボン未接続編集などの補完

### なぜ「ほぼずれない」と言えるか

- 再オープンで消える状態（例: `View.ShowAll`）は **ログベース採点**に寄せ済み（1-1 等）
- 離脱時・採点直前の **ログ補記**が厚い（`Project_summer` 時代より改善）
- 残る典型は **その場〇のあと〜一括までに破壊的操作を足した**ケース

### 推奨対応

- 急がない。問題報告があればタスク単位で証跡を見る。

## Excel

### アーキテクチャ

| | その場 | 一括 |
|--|--------|------|
| 入口 | `AppBarWindow` → `MainViewModel.ExecuteScoreAsync` | `ReviewPageWindow.ScoreAllProjects` |
| 文書 | ActiveWorkbook（未保存含む／一部 `SaveCopyAs`） | 保存→Close→パスから再 Open |
| チェッカー | 同一 `ExcelChecker*` | 同左（呼び出し方が違う） |
| ゲート | `ExcelScoreExplanation.Apply`（主に `[Op]`） | 同左（ループ内 Apply） |
| 呼び出し | 公開 `CheckTask_*()` | `*_Impl(filePath)` 優先 |
| 共有モジュール | なし（二重実装） | なし |
| Executed 正答証跡 | ほぼ未使用（`LogCommand` は定義のみ） | 同左 |

主要ファイル:

- `MOSapp/mos_xaml_app/Ui/ViewModels/MainViewModel.cs`
- `MOSapp/mos_xaml_app/Views/ReviewPageWindow.xaml.cs`（`CheckTaskMethodBinding`）
- `MOSapp/mos_xaml_app/Libraries/ExcelScoreExplanation.cs` / `ExcelLogReader.cs`
- VSTO: `ExcelAddIn1`（boundary flush、`AddChart` Selection 記録）

### 差が出うる要因

1. 開いたまま（未保存）vs 保存再オープン  
2. ActiveWorkbook vs 指定パスの Impl  
3. boundary flush の成否（その場開始／レビュー前。一括ループ中は追加 flush なし）  
4. ログ依存の正答（例: 4-2/4-3 の作成時 Selection）  
5. 採点後の追加破壊操作（Word と同様）

### 4-2 / 4-3 について

- **作成時**の Selection 補記はある（挿入直後が1セルでも、直前の複数セル選択を書く）
- Word 型の「離脱時に証跡を書き直す」補記ではない
- チェッカーは今もログの `AddChart` Selection を必須とする

### やっては弱い修正（不都合が出やすい）

| 直し方 | リスク |
|--------|--------|
| その場も保存済みファイルだけ見る | その場が厳しくなり、未保存の正しい作業が × |
| 4-2/4-3 でログをやめて系列だけ見る | 手順判定の意図とずれる／誤 ○・誤 × |
| 破壊検知を闇雲に厳しくする | 以前 ○ が × に |
| 巨大リファクタ一気 | 回帰 |

### 推奨対応（判定を変えない方向）

1. **採点経路の共通化**（優先）  
   - `Libraries` に `ScoreProject` 相当を切り出し（一括側の Binding + 毎タスク Apply を正とする）  
   - 一括を先に乗せ → その場を `filePath: null` で同じ核へ  
   - UI・Excel 開閉・flush タイミングは呼び出し側に残す  
   - `UiTestAppBar`（ゲート無し）は後回し可  

2. **証跡確定を厚くする**（経路と別レーンで可）  
   - 「無いものを推測して合格」ではなく「取りこぼしを書く」  
   - 対象は正答に必要なもの＋既存レイアウト差分に限定（余計な `[Op]` で破壊 ✖ を増やさない）

### 実装タイミング

- アプリでその場／一括の〇✖比較ができるまで **実装は待つのが安全**  
- Apply タイミングや公開 vs Impl の差で、意図せず正誤が動く可能性はゼロではない

## PowerPoint

### アーキテクチャ

| | その場 | 一括 |
|--|--------|------|
| 入口 | `UiTestAppBarWindow` → `MainViewModel.ExecuteScore` | レビュー → `ScoreAllProjects` |
| 文書 | 開いたまま | 保存→閉じて `.pptx` 再 Open |
| 本体 | **共通** `PowerPointGrader.GradeTask` | 同左（`batchScoring` / snapshot skip あり） |
| 証跡 | 離脱境界の補記が厚い | Word 型の採点直前 flush は **なし** |
| ScoreExplanation | なし | なし |

主要ファイル:

- `MOSapp/Mos PowerPoint Mogi App/PowerPointGrader.cs`
- `MOSapp/Mos PowerPoint Mogi App/Views/UiTestAppBarWindow.xaml.cs`（`ScoreAllProjects`）
- `MOSapp/Mos PowerPoint Mogi App/MainViewModel.cs`
- `MOSapp/Mos PowerPoint Mogi App/Libraries/PPLogReader.cs`（`IsBatchScoring`）
- VSTO: `PowerPointAddIn1`（境界・印刷・光彩等の補記）

### 差が出うる要因

1. 再オープンで消えやすい状態／メディア COM  
2. 採点直前の汎用 Evidence Flush が無い（境界取りこぼし）  
3. `IsBatchScoring` によるリトライ差（例: P9）  
4. snapshot skip 失敗時の破壊ゲート  
5. 採点後の追加破壊操作

### 推奨対応

- **Excel のような経路共通化は第一優先ではない**（すでに `GradeTask` で共有）
- 効くのは:
  1. Word に近い **採点直前の証跡 Flush**
  2. 必要なら batch 専用リトライ／reopen 差分の見直し
  3. 余力で `ScoreAllProjects` のモジュール切り出し（可読性）

## 3アプリ横断

```text
成熟度（その場＝一括の揃いやすさ）:  Word ＞ PowerPoint ＞ Excel

ずれの主因:
  Word  … 採点後の追加操作が主
  PP    … reopen / flush 不足 / batch 専用分岐
  Excel … 経路二重 + ファイル状態依存 + 一部ログ正答
```

### 次のアクション案

1. ~~Word / Excel / PP 調査~~（本メモ）  
2. アプリ起動・〇✖比較が可能になったら:
   - Excel: `ScoreProject` 共有化（一括 → その場）※判定ロジックは触らない  
   - 必要に応じ Excel / PP の証跡確定を厚くする  
3. Word は現状維持で監視

### 実装プロンプト用（Excel 経路共通化）

再開時に渡す要約:

- 判定ルール・免除・チェッカー本体は変更しない  
- `ReviewPageWindow` の Binding + 毎タスク `ExcelScoreExplanation.Apply` を正とし、`Libraries` に `ScoreProject` を抽出  
- 一括のみ差し替え → 確認 → その場を同じ核へ（`filePath: null` 可）  
- flush / Excel 開閉は呼び出し側のまま  
- 実装後、同じ操作でその場と一括の〇✖を比較する
