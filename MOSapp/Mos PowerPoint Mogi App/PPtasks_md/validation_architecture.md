# 採点チェック・破壊的操作検知の仕組み

このドキュメントでは、MOS模擬試験アプリにおける採点機能と、ユーザーがタスクの指示にない誤った操作（破壊的操作）を行ったかどうかを検知する一連の仕組みについて解説します。

## 全体像（アーキテクチャ / 現行実装）

採点および破壊的操作の検知は、**「試験アプリ側」**と**「PowerPoint VSTOアドイン側」**の2つが連携して動作します。
この2つは、直接通信するのではなく `%TEMP%` フォルダ内に作成された **共有ファイル（テキストファイル）** を介して情報をやり取りしています。

### 主なデータの流れと判定のタイミング

1. **タスク開始時**:
   ユーザーがアプリバーから試験を開始したり、タスクを切り替えたりすると、現在どのタスクを実行中かという情報（免除条件を含む）が共有ファイルに書き込まれます。
   アドイン側はそれを検知し、その時点のプレゼンテーションの「スナップショット（現在の状態）」をファイルに保存します。

2. **操作中（裏側の監視）**:
   ユーザーがタスクの指示に従って操作します。タスクを切り替える（次の問題へ進む）タイミングで、アドイン側は保存しておいた「開始時のスナップショット」と「移動直前の状態」を比較し、本来変更してはならない部分（例: 触ってはいけない図形の移動、余計な文字入力など）があれば、「破壊的操作エラー」としてログファイルに記録します。  
   現行ではこれに加えて、`MoveToNextProject()` 側でも遷移直前に `PPSnapshotChecker.CompareAndGetErrors()` を実行し、検知エラーを `mos_ppt_destructive_errors.log` に追記しています。

3. **採点ボタン押下時（リアルタイム監視）**:
   試験アプリ側は、採点開始時に以下の2つのチェックを行います。
   - **過去のログチェック**: アドインが記録した「破壊的操作エラー」の履歴がないかを確認します（これで、タスク遷移時に裏で行われた不正操作を検知します）。
   - **スナップショットのリアルタイムチェック**: 現在のPowerPointの状態と、開始時のスナップショットを再度比較します（これで、採点ボタンを押す直前に行われた不正操作を検知します）。

   これらのチェックをすべてクリアした場合のみ、本来のタスクごとの機能チェック（COM検証）へ進みます。

## 主要な C# ファイルの役割（現行）

### 1. タスク管理・免除設定
*   **`PPTaskValidationConfig.cs`**
    *   **役割**: 各プロジェクト・各タスクにおいて、**「どの項目の変化を許容する（免除する）か」**を定義する設定ファイルです。
    *   **詳細**: `PPValidationExemptFlags` というフラグ（`SlidesCount`, `ShapesCount`, `TextLength`, `ShapePosition` など）を定義しています。例えば、「文字のみ入力するタスク」では `TextLength` の変化を許可し、それ以外のスライド追加などが行われた場合は不正とみなす、といったルールがプロジェクト単位で記述されています。

### 2. 試験アプリ側のファイル
*   **`Views/UiTestAppBarWindow.xaml.cs`**
    *   **役割**: アプリバーのUI制御。タスクが切り替わった際に `WriteCurrentTaskFile()` を呼び出し、現在のプロジェクト番号、タスク番号、および上記の `PPTaskValidationConfig` から取得した「免除フラグ」をセットで `%TEMP%\mos_ppt_current_task.txt` に書き込み、VSTOアドインにタスク開始を通知します。
*   **`PowerPointGrader.cs`**
    *   **役割**: 「採点」ボタンが押下された際に呼ばれるメインの採点クラスです。
    *   **詳細**: タスクごとのロジック（`PowerPointChecker1_X` など）を呼び出す前に、`HasLoggedDestructiveError()`（破壊的操作ログ確認）→ `FailsLogChecks()`（許可外ログ操作確認）→ `PPSnapshotChecker.CompareAndGetErrors()`（リアルタイム比較）の順でチェックします。いずれかでエラー（不正な変更）があれば、即座に「✖（不合格）」を返します。
*   **`Libraries/PPSnapshotChecker.cs`**
    *   **役割**: リアルタイムのスナップショット比較エンジン。
    *   **詳細**: `mos_ppt_snapshot.txt` （開始時の状態）を読み込み、現在の PowerPoint 上の「スライド数」「図形の数」「スライド単位の文字数」「総テキスト文字数（`TextFrame2`優先）」「アニメーション数」「図形の座標」を取得して比較します。免除フラグ（ExemptFlags）に加えて、`PPTaskValidationConfig` のタスク別デルタ判定（図形数/文字数）や既存図形変更数の上限判定を適用し、免除タスクでも指示外操作を検知します。
*   **`Libraries/PPLogReader.cs`**
    *   **役割**: VSTO側が吐き出した各種ログファイルやスナップショットファイルのパスを一元管理し、読み込みや削除の機能を提供します。
*   **`PowerPointProjectResetHelper.cs`**
    *   **役割**: プロジェクトのリセット機能。
    *   **詳細**: リセットボタン押下時に、ファイルを初期状態に上書きするだけでなく、`mos_ppt_destructive_errors.log` （破壊的操作ログ）や `mos_ppt_snapshot.txt` （スナップショット）などを確実に削除（クリア）し、新しくクリーンな状態で記録を開始できるようにします。

### 3. VSTOアドイン側（PowerPoint常駐）のファイル
*   **`PowerPointAddIn1/ThisAddIn.cs`**
    *   **役割**: PowerPointの裏で動き続ける監視プログラム。
    *   **詳細**: タイマーを使って `%TEMP%\mos_ppt_current_task.txt` を定期的に監視しています（`TaskFilePollTimer_Tick` / 500ms）。
        *   **タスク遷移の検知**: タスク番号の切り替えを検知すると、まず「古いスナップショット」と「現在の状態」を比較し、不正操作があれば `mos_ppt_destructive_errors.log` に書き出します（`CheckAndLogDestructiveOperations`）。
        *   **スナップショットの取得**: その後、「新しいタスクの開始時の状態」を正確に取得し、`mos_ppt_snapshot.txt` として保存し直します（`TakeUnifiedSnapshot`）。
        *   **補助ログ監視**: 破壊的操作検知とは別に、印刷設定・グレースケール・音声設定・キオスク設定・レイアウト複製をポーリングし、タスク判定用ログを出力します。

## 共有・連携ファイル（%TEMP% フォルダ内）

*   **`mos_ppt_current_task.txt`**
    *   現在実行中のタスク情報をアプリが書き込み、VSTOが読み取るためのファイル。
    *   **フォーマット**: `[ProjectId],[TaskId],[ExemptFlags(整数)]`
*   **`mos_ppt_snapshot.txt`**
    *   VSTOがタスク開始時に記録したプレゼン状態の各種データ。
    *   **内容**: スライド数、総文字数、スライドごとの図形数、一部の図形の座標など。
*   **`mos_ppt_destructive_errors.log`**
    *   タスクの切り替え時に、VSTOが検知した「破壊的操作（エラー）」を記録するファイル。
    *   **フォーマット**: `[ProjectId],[TaskId]:エラー詳細1 | エラー詳細2 ...`
    *   アプリ側（`PowerPointGrader`）はこのファイル内に現在のタスクの記録が含まれていないかをチェックします。

## 破壊的操作（エラー）として検知される内容

本システムでは、以下の項目を「タスク開始時のスナップショット」と「現在の状態」で比較し、**タスクの指示にない変更（= 破壊的操作）**が行われていないかを監視しています。変更が検知された場合、即座に「✖（不合格）」となります。

### 監視対象の項目とエラー内容
1. **スライド数の変化 (`SlidesCount`)**
   *   **エラー内容**: スライドの追加や削除が行われた場合、およびスライドの順序（名前）が入れ替わった場合にエラーとなります。
2. **図形数の変化 (`ShapesCount`)**
   *   **エラー内容**: 各スライドに配置されている図形（プレースホルダー、画像、テキストボックス、SmartArtなど）の追加や削除が行われた場合にエラーとなります。
3. **テキスト文字数の変化 (`TextLength`)**
   *   **エラー内容**: プレゼンテーション全体の総文字数（プレースホルダーやテキストボックス内の文字）が増減した場合にエラーとなります。（例: 不要な文字を入力したり、既存の文字を誤って消してしまった場合）
4. **アニメーション数の減少 (`AnimationRemoved`)**
   *   **エラー内容**: 既存のアニメーションが削除されて数が減った場合にエラーとなります。（追加される分にはこの項目ではエラーになりません）
5. **図形の座標・サイズの反転 (`ShapePosition`)**
   *   **エラー内容**: 各スライドの個別の図形の「左位置(Left)」「上位置(Top)」「幅(Width)」「高さ(Height)」が、元の状態から 0.5 ポイント以上変化した場合にエラーとなります。（誤って図形をドラッグして動かしたり、サイズを変えたりした場合）
6. **リボンコマンドの不正使用 (`RibbonCommand`)**
   *   **エラー内容**: VSTO標準のログ(`mos_ppt_log.txt`)をチェックし、問題の指示と関係ない特定のメニューやボタンが操作されていないかを確認します。

### 免除設定（PPValidationExemptFlags）による例外処理
タスクの中には「新しいスライドを追加する」「文字を入力する」といった、上記の監視項目に引っかかる操作そのものが正解となる場合があります。

そのため、`PPTaskValidationConfig.cs` にてタスクごとに **免除フラグ（例: `PPValidationExemptFlags.TextLength`）** を設定し、「このタスクでは文字数の変化は見逃す（許可する）」といった柔軟な調整を行っています。
また、スライド追加や図形の追加を行うタスクでは、連動して「アニメーションの減少」などの関連エラーも自動的に免除される仕組みを取り入れています。

### 現在の追加制約（免除時の厳格化）
現行実装では、単純な「フラグ免除」だけではなく、以下の制約を併用しています。

1. **図形数のスライド別デルタ制約**
   * `GetAllowedShapesCountDelta` / `IsAllowedShapesCountDelta` により、免除タスクでも「どのスライドで何個まで増減可」を判定します。
   * 例: `3-4` はスライド1で `0` または `+2` を許可、`5-5` はスライド3で `0` または `-2` を許可。

2. **文字数のスライド別デルタ制約**
   * `GetAllowedTextLengthDelta` / `IsAllowedTextLengthDelta` により、免除タスクでも想定外の文字変更を検知します。
   * 例: `1-7` はスライド1で `0` または `+5`、`9-6` はスライド1で `0` または `-57` を許可。

3. **図形位置免除時の既存図形制限**
   * `IsShapePositionExemptForNewShapesOnly` により「新規追加図形のみ免除（既存図形の変更は禁止）」をタスク単位で適用します。
   * `GetAllowedExistingShapePositionChangeCount` により、既存図形の変更を許可する場合でも「変更可能数の上限（例: 1個）」を設定します。

## バックアップファイル生成設定

`Views/UiTestAppBarWindow.xaml.cs` の `MoveToNextProject()` では、`App.config` の `EnableProjectBackup` を参照してバックアップ保存を実行します。  
現在の設定は次のとおりです。

* `App.config`
  * `<add key="EnableProjectBackup" value="false" />`

このため、**現状はプロジェクト遷移時の backup ファイル生成は OFF** です。

## `[Perf]` デバッグ出力の運用方針

採点処理には、待機・比較タイミングを観測するための `[Perf]` デバッグ出力（`StartTaskAndWaitForSnapshot` や `PPSnapshotChecker` 周辺）を入れています。  
運用方針として、**以下の事象が発生しないことを確認できた場合は、`[Perf]` デバッグ出力を削除する**ものとします。

1. `timeout 2000ms` が1回の採点フロー内で複数回出る
2. `id mismatch` が毎回同じ箇所で再現する
3. 上記に伴って採点結果に実害（誤判定）が見える

### 正誤判定への影響（変更方針）

以前に共有した通り、次のような **「待ちを安定化するだけ」の改善** は、採点条件そのものを変えないため、正誤判定を狂わせるリスクは低いです。

* タイムアウト値を少し延長する
* ポーリング間隔を調整する
* スナップショット一致の連続確認を入れる

一方で、次のような変更は判定精度に悪影響が出る可能性があるため、原則避けます。

* `mismatch` 時に無条件でチェックをスキップする
* タイムアウト時にチェック条件を緩める

### Perfログ削除判断チェックリスト（運用用）

`[Perf]` デバッグ出力を削除する前に、以下を確認します。

1. **再現テスト（複数回）**
   * 同一タスク遷移・同一採点操作を複数回実施し、`timeout 2000ms` 多発が再現しないこと。
   * `id mismatch` が同じ箇所で固定的に再現しないこと。

2. **採点結果の健全性確認**
   * 正解操作で合格、不正操作で不合格となることをサンプルケースで確認。
   * 過去に誤判定が発生したケースがあれば、再実行して再発しないこと。

3. **変更内容の分類確認**
   * 実施した変更が「待機安定化（タイムアウト/ポーリング/一致確認）」の範囲に収まっていること。
   * 判定条件そのものを緩和していないこと（無条件スキップ等が無いこと）。

4. **削除後の最終確認**
   * `[Perf]` 出力を削除しても採点の正誤判定が変わらないこと。
   * 必要最小限のエラーログ（不合格理由の追跡に必要な情報）は維持されていること。
