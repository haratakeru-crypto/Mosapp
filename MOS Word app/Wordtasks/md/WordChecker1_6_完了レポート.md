# プロジェクト6 採点機能 改修完了レポート

プロジェクト6（表操作）全7タスクの採点ロジック改修が完了したため、最終的な実装方針・判定ロジック・実装上の知見をまとめる。
本レポートはプロジェクト7以降の改修における **設計指針・判断基準・ハマりどころ集** としても活用可能。

---

## 共通の設計指針

1. **ターゲット特定ロジック**
   - `GetTableXmlNearText(xml, "キーワード")` を使用し、対象の見出し直後の表ブロック（`<w:tbl>`）を特定してから解析する。
   - これにより、文書内に複数の表があっても誤判定を防ぎ、かつCOM解放漏れによるクラッシュを回避する。
2. **アドイン（VSTO）の制約**
   - `TableSplitTable` や `TableSplitCells` は `idMso` としてフックできないため、これらは操作ログに頼らず、XMLの最終状態（State）のみで判定する。

---

## 判定方針の決定フロー（重要）

**「XML化が常に最適」ではない**。タスクごとに以下のフローで判定方針を決定すること。

```
[1] 操作の最終状態に、ユニークなXMLタグや属性値が残るか？
    ├─ 残る   → [2] へ
    └─ 残らない → COMのまま、または操作ログのみで判定（VSTO制約に注意）

[2] 同じXML最終状態を「誤った操作・手動操作」で作れてしまうか？
    ├─ 作れる   → XML判定 + ログ記録 AND（誤学習防止）
    └─ 作れない → XML判定のみ（リボン/ダイアログ/右クリック等の正解ルートをすべて許容）

[3] 既に正しく動作していて、対象表が事実上ユニークに絞れるなら？
    └─ 現状維持（COMのまま）も有効な選択肢（改修リスク回避）
```

### 方針別の代表例

| 方針 | 例 | 理由 |
| :--- | :--- | :--- |
| **XML のみ** | 6-1, 6-2, 6-3, 6-4, 6-6 | 最終状態に一意なタグ/属性が残り、誤操作で同状態を作れない。ダイアログ・右クリック経由の正解ルートも許容できる。 |
| **XML + ログ AND** | 6-5 | 「手動で各列を同じ幅に設定」しても XML 上は均一になるため、ボタン操作（`TableColumnsDistribute`）の記録がないと誤学習を許してしまう。 |
| **COM のまま** | 6-7 | 13行3列＋特定テキスト3語という条件が事実上ユニーク。動いている実装を壊すリスクを避けて現状維持を選択。 |

## 技術リファレンス（XMLタグ名）

- **表の繰り返し設定**: `<w:tblHeader />` （`<w:trPr>` 内に存在）
- **列幅の均等化**: `<w:tblGrid>` 内の `<w:gridCol w:w="..." />` の値を比較。
- **文字列の幅に合わせる**: `<w:tcW w:type="auto" />` （セル単位）および `<w:tblW w:type="auto" />` （表単位）。
- **セルの分割・結合**: `<w:gridSpan w:val="数値" />`。
- **文字の輪郭・塗り**: `<w14:textOutline>`, `<w14:textFill>`（`<w:rPr>` 内）。配下に `<w14:schemeClr w14:val="accent2">` や `<w14:srgbClr w14:val="ED7D31">` などで色を表現。
- **影・反射・光彩**: `<w14:shadow>`, `<w14:reflection>`, `<w14:glow>`（`<w:rPr>` 内）。

## 実装上の注意点（プロジェクト7以降にも適用）

### Regex 関連
- `Regex` を使用する際は、`System.Text.RegularExpressions.RegexOptions.Singleline` を指定して、タグが複数行にまたがっていてもマッチするようにすること。
- 内容（テキスト）をチェックする際は、XMLタグを除去したプレーンテキストで比較するか、`Contains` で柔軟に判定すること。

### キーワード指定のハマりどころ（最重要）
- `GetTableXmlNearText` のキーワードに **章番号（`1.`, `2.` など）を含めない** こと。
  - 見出しスタイルの自動番号は `<w:numPr>` で表現され、テキストノードとしてXMLに存在しないため、`"2.北海道..."` は永久にヒットしない。
  - 正：`"北海道のうまいもの市場売上"` ／ 誤：`"2.北海道のうまいもの市場売上"`
- 同じ理由で、リスト番号・脚注番号など「自動生成される文字」は検索文字列に含めない。
- 一方、段落内でランが分割されている場合（書式が途中で変わって `<w:r>` が複数になる場合）は `GetTableXmlNearText` 側でタグ除去してから `Contains` するため吸収できる。

### 距離制限
- `GetTableXmlNearText` は見出し段落の直後 **10000 文字以内** の最初の `<w:tbl>` を返す。
  - 当初500文字だったが、間に挟まる段落（例：「単位:千円」）の書式情報量で簡単に500を超えるため拡張した。
  - 文書構造を変える際は念のためこの値の妥当性を再確認すること。

### Ribbon.xml と Ribbon.cs の優先順位（最重要）
- VSTO アドインのリボン UI と idMso フックは **`Ribbon.xml`（リソース）が実体**であり、`Ribbon.cs` 内のハードコード XML はフォールバックに過ぎない。
- **操作ログを使う方針（XML + ログ AND）を採用するタスクでは、必ず以下を事前確認すること**：
  1. 対象の `idMso`（例：`TableColumnsDistribute`、`TableRepeatHeaderRows`）が `Ribbon.xml` の `<commands>` 内に登録されているか。
  2. 登録されていない場合は `<command idMso="..." onAction="CommandOnAction" />` を追加してビルド・再インストール。
  3. ログファイル（`%TEMP%\mos_word_log.txt`）に該当 `idMso` が記録されることを動作確認。
- `Ribbon.cs` だけ書き換えても XML が読み込まれている限り反映されない点に注意。
- なお、`TableSplitTable` / `TableSplitCells` のように **そもそも idMso でフックできないコマンド**も存在するため、操作ログ方針を決める前に hookability を確認すること。

### COM 利用時の安全策
- `Marshal.GetActiveObject("Word.Application")` の取得失敗時に `new Application()` を起動するパターンは避ける（採点中に新規 Word プロセスが立ち上がるリスク）。失敗時は素直に `return false` する。
- COM オブジェクトは取得した順に `Marshal.ReleaseComObject` で解放する。`finally` で `document` を解放するパターンを既存実装に合わせる。
- 可能な限り COM への依存を減らし、`document.WordOpenXML` を取得した後は XML 上で完結させる。

### デバッグ手法
- 判定が想定通りにならない場合は、**段階ごとの結果を出力**するデバッグ関数を一時的に仕込む。
  - 出力先：`System.Diagnostics.Debug.WriteLine`（Visual Studio 出力ウィンドウ）+ `C:\temp\<task>_debug.txt`（ファイル）の両方が便利。
  - `System.Windows.Forms.MessageBox` は参照追加が必要なため、上記2系統を推奨。
- 1行目XMLやサブブロックを `C:\temp\xxx.xml` にダンプして、Word側で実際に生成される構造を確認する手法は 6-4 などで有効だった。
- 正解動作後・誤動作後の XML を比較し、差分から判定条件を組み立てる。
- **解決後は必ずデバッグコードを削除**（ログファイルへの追記もコストになるため）。

### 効果系（6-4 系）特有の注意
- 「文字の効果と体裁」の各プリセットは、`<w14:textOutline>` の有無や `<w14:shadow>` 等の有無で互いに区別される。
  - 単に「輪郭がオレンジ」だけで判定すると、別プリセット（影付き等）にも誤判定する。
  - 「輪郭ブロック内に accent2/ED7D31」「塗りブロックも同じ色」「影/反射/光彩なし」のように **タグ位置で限定** すること。
- フォント色のみで accent2 を設定した場合は `<w:color w:themeColor="accent2"/>` になり、`<w14:textOutline>` は生成されない。両者は明確に異なるパターンとして扱うこと。

### MOSの採点ポリシーと許容範囲
- リボンボタン・右クリックメニュー・ダイアログのチェックボックスなど、**同じ結果が得られる操作はすべて正解として許容**するのが基本。
  - 例：6-3 のセル分割は右クリックでも可、6-6 のタイトル行繰り返しは表のプロパティダイアログでも可。
- ただし、6-5 のように「結果は同じだが意図・学習価値が異なる操作（手動で同じ幅にする等）」を区別したい場合は、ログ AND で操作経路を縛る。
- どちらの方針が適切かは「**そのタスクで何を学んでほしいか**」を基準に判断する。

### 既存実装の改修判断
- すでに採点が正しく動作しているタスクは、**形式的なXML化のためだけに改修しない**。
  - 改修によるリグレッションリスクと、改修で得られる安定性向上を比較する。
  - 6-7 のように「対象表が事実上ユニークに絞れる」ケースは現状維持が合理的。
- 改修対象になるのは原則として以下のいずれか：
  1. 現状で × になる／不安定（誤判定が出る）。
  2. COM特有のクラッシュ・リーク・タイムアウトのリスクが顕在化している。
  3. 同様の操作を別タスクでXML化済みで、整合性のために揃えたい（ただし無理に揃えない）。

## プロジェクト6 改修の主な成果

1. **判定精度の向上**
   - 6-3: 「1行目=4セル かつ 他行=2セル」の厳密化で誤学習リスクを排除。
   - 6-4: 「文字の効果と体裁」プリセットを輪郭ブロック単位で識別し、フォント色変更との混同を解消。
   - 6-5: 操作ログAND判定で「手動で同じ列幅を設定」する誤学習パターンを除外。
   - 6-6: 全表ループから「見出し直下の表のみ」に対象を厳密化。
2. **安定性の向上**
   - COM呼び出しを削減し、Word再起動なしでも採点可能に。
   - `Marshal.ReleaseComObject` の解放漏れリスクを大幅低減。
3. **ナレッジの体系化**
   - 判定方針の決定フロー、Ribbon.xml優先性、自動番号の落とし穴など、後続プロジェクトに転用可能な知見を本ドキュメントに集約。
